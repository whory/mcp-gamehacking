# DMA Attack

PCIe Direct Memory Access threat modeling for game security: identify the **memory initiator**, **transport**, **required privilege**, **isolation boundary**, and **observable artifacts** before classifying a technique as DMA or attributing a product. Then map FPGA endpoints (often M.2), host tools like [[pcileech]]/MemProcFS, and defenses software anti-cheat alone cannot fully cover once a hostile bus-master can read RAM.

## Classify the acquisition path first

Use [[memory-acquisition-path]] to separate hardware bus access from host-mediated software capture. Record source access requirements, transport endpoints, analysis location, write capability, and optional input paths independently. Map controls to the real boundary—device remapping, driver/interface security, authenticated transport, or server-side exposure—not a library brand or two-PC topology alone. Apply [[research-rigor]] to disputed implementation, performance, compatibility, or detectability claims; classification does not prove a commercial setup uses advertised components.

## Threat model

Typical external DMA cheat: **cheat PC** (signatures, ESP, aim logic) + **DMA card** (FPGA in an M.2 or add-in slot issuing Memory Read TLPs) + optional **HID actuator** (USB keyboard/mouse emulator). No attacker code need run on the gaming OS—the machine sees a PCIe device performing ordinary-looking DMA mediated by chipset and (when configured) the [[iommu]].

## Three defense layers

| Layer | Property evaluated | Limits |
|-------|-------------------|--------|
| PCIe identity and behavior | Consistency with an identified device and matched baseline | Mismatch needs version, topology, driver, workload, and benign-device context; an identifier is not proof of intent |
| [[iommu]] enforcement | Device requests permitted by active remapping policy | Verify actual path, mappings, lifecycle, and fault evidence; enforcement and observation are separate |
| External attestation | Authenticity and policy appraisal of selected measurements | Boot evidence does not automatically cover current device behavior or runtime mapping state |

Hypervisor containment ([[hvci]], EPT traps, honeypot pages) and firmware policy (pre-boot DMA protection, BIOS DXE hardening in [[x670e-tomahawk-anticheat-update]]) stack on top. **Assurance boundaries:** see [[assurance-boundaries]]—separate mechanism, deployed policy, evidence coverage, and attribution; do not treat Kernel DMA Protection “On,” HVCI, or a valid TPM quote as proof of every endpoint’s runtime ATS state or absence of DMA-capable hardware.

## PCIe stack (detection-relevant)

- **TLPs:** Memory Read/Write, Config R/W, Completions; Requester ID (BDF) drives IOMMU lookup; completion splitting (MRRS/RCB/MPS) and tag turnover are donor-class fingerprints.
- **Config Space:** 256-byte legacy header + extended capabilities (AER, DSN, ATS, ACS, SR-IOV); capability-chain walk, BAR mask probe, R/W consistency on Command/Device Control and W1C bits. Kernel config-space tooling such as [[pcie-detector]] (gmh5225; C++ driver) supports defensive inventory beyond user-mode dumps for anti-cheat engineers in the Detection:DMA lane. User-mode scanner/forensics tooling such as [[drvscan]] (ekknod; C; PCIe enumeration plus pcileech-style physical-memory signature scans for cheat/rootkit residue) complements that inventory lane. Server-administrator integrity suites such as [[irontrace]] (codedevdev; C# WPF/CLI; PCI/PCIe/USB/driver watchlists, DMA masquerade indicators, LOLDrivers correlation, explainable JSON verdicts without auto-ban; optional self-hosted triage) aggregate PCIe/USB/driver signals for human review in the Detection:DMA lane.
- **Behavioral:** LTSSM/link width, ASPM transitions, AER correctable-error baselines, MSI/MSI-X interrupt distribution, completion-latency distribution (KS / Anderson–Darling vs donor reference).

Stock [[pcileech-fpga]] builds expose trivial signals (placeholder `10EE:0666`, zerowrite4k BAR, missing AER). Sophisticated firmware adds shadow config, overlay RAM, BAR MMIO + MSI behavior, and donor-matched link/interrupt/latency profiles. Prefer **device evidence dimensions** over informal tier labels:

| Dimension | Evidence needed | Permitted conclusion |
|-----------|-----------------|----------------------|
| Identity and provenance | Inventory, exact IDs, trusted source/version | Consistent, inconsistent, or unverified identity |
| Configuration and function | Device contract + matched observations | Specific conformance discrepancy |
| Runtime behavior | Collector coverage, workload/power baseline | Calibrated anomaly within measured conditions |
| Memory-access policy | Active remapping + available fault evidence | Permitted or denied access on the established path |
| Platform trust | Attestation policy + supported runtime observations | Trust in measured properties; unmeasured state explicit |

No label establishes guaranteed detection or a required trust anchor; reference-set absence is unknown identity, not proof a class is malicious or exhausted. Donor-cloning generators such as [[pcileechgen]] automate scan/check/build/validate workflows: Linux VFIO donor capture → SystemVerilog/COE → Vivado bitstreams with dynamic BAR emulation, NVMe admin-queue/DMA bridge, offline MMIO trace import, and TLP latency tuning across many PCILeech-compatible boards.

## IOMMU and bypass surface

Before treating VT-d/AMD-Vi as active protection, separate **ACPI advertisement**, **Windows policy** (KDP / per-device DMA Remapping Policy), **live unit state**, and **per-requester coverage**—do not collapse them into one boolean. See [[iommu-state-verification]].

Legitimate drivers map only explicit IOVAs; game memory should stay outside device domains. Active cheat paths include IOMMU disabled, pre-boot DMA, identity/passthrough domains, driver page over-allocation (Thunderclap class), **legitimate-path exfil** (spoofed NIC reading its own RX ring), and kernel reprogramming of IOMMU tables via [[byovd]]. Windows PoC [[diedmaprotection]] demonstrates runtime disable of DMA remapping (IOMMU/VT-d) from a kernel driver to re-enable FPGA [[pcileech]]-class physical reads. Defensive sample [[dmaprotect]] programs VT-d/AMD-Vi remapping tables from kernel mode to block unauthorized PCIe DMA while allowing legitimate devices—illustrating the mitigation side of the same remapping surface. kEv1nZ0/[[vtd-bypass]] (Python; LeechCore/FPGA physical-memory writes; XSDT/DMAR ACPI table fabrication so firmware-disabled VT-d reads as enabled; boot-window timed patches; Cheat / VT-d/IOMMU) adds **ACPI spoofing via DMA** beside driver-mediated remapping edits. ACS Source Validation + P2P redirect and ATS-untrusted policy for untrusted endpoints are mandatory in threat models. See [[iommu]] for the condensed bypass catalog.

## Layered detection pipeline

Apply [[research-rigor]] when turning signals into enforcement.

1. **Pre-game:** IOMMU + IR active, Secure Boot, VBS/[[hvci]], TPM provisioned, attestation Quote, ACS topology walk, full 4 KB config dump per device, SMBIOS slot cross-check.
2. **PCIe integrity:** VID/DID allowlists, signature residue, BAR/class probes, R/W and W1C probes, link/AER baselines, latency statistics.
3. **Runtime:** per-device IOMMU fault rate, interrupt accounting, cheat-phase access patterns (discovery → narrow periodic reads), honeypot regions with fault/EPT logging.
4. **Containment before verdict:** sandbox domain remapping, Bus Master Enable clear, DPC; correlate multi-signal evidence server-side.

Firmware matching donor behavior on tested dimensions can evade isolated PCIe/IOMMU signatures—external trust anchors (TPM PCR[7] DMA Protection Disabled, DRTM, remote attestation) address gaps bus-layer checks cannot prove alone. **Realistic limits:** a passing identity or behavioral check is consistency only in observed dimensions; a denied DMA request bounds that request, not every device; valid attestation covers selected measurements, not all current memory access. Report coverage, missing evidence, shared failure modes, and measured error rates instead of evasion checklists.

## Key sub-areas

- **Acquisition classification:** [[memory-acquisition-path]] — initiator vs transport vs analysis site
- **PCIe stack:** TLPs, Config Space, BAR probing, MSI/MSI-X, AER, link/ASPM behavior; collectors must respect configuration ownership (no unauthorized BME/MSI toggles on live devices)
- **Firmware evidence:** stock pcileech fingerprints → donor shadow config → overlay RAM → behavioral emulation
- **[[iommu]]:** VT-d / AMD-Vi domains, ACS, ATS-untrusted policy, fault-rate monitoring, containment
- **Hypervisor / attestation:** EPT CPU permissions ≠ device DMA; VBS/[[hvci]]; TPM Quote + measured-boot PCRs with profile-specific interpretation
- **Thunderbolt/USB4:** hot-plug PCIe tunneling (SL0–SL3), Thunderclap-class bypasses, Kernel DMA Protection for runtime hot-plug; pre-boot DMA remains a firmware responsibility
